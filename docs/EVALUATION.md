# 効果測定（代役の利用者テスト）

masume と同じく、利用者役のエージェントに実際の依頼文だけを渡して使わせ、詰まった所を直して測り直す。

## 1回目の題材（2026-11-19）

移行案件の SIer エンジニア役。ツールのコードを読まず、README と SKILL.md だけを頼りに作業する。

- データ：社員マスタ `EMPMAST.dat`（Java で独立に作成。IBM939、RDW 付き可変長、6件、1件149バイト＋RDW 4バイト）
- コピーブック：`EMPMAST.cpy`（Shift_JIS、1〜6桁目に連番、73桁目以降に識別子がある固定形式）
- 依頼：①件数とコードページ ②山田太郎の給与と手当合計 ③データの問題をすべて ④新入社員2名のテストデータを作って確認
- 代役には知らせずに仕込んだ問題（正解）
  | 社員 | 項目 | 仕込んだ問題 |
  |---|---|---|
  | E0000003 | ALLOWANCES(1).ALLOW-NAME | 漢字の後ろの SI（0F）が消えている |
  | E0000004 | EMP-NAME-KANJI | 外字（ユーザー定義領域 6941）が入っている |
  | E0000005 | BONUS-RATE | 数値項目が空白（40 40 40） |
  | E0000006 | DEPT-CD | 部署コードに英字（C1 F1 C2 F2 = "A1B2"） |
- 正解：①6件・IBM939・RDW ②給与 350,000、手当合計 32,000（通勤 12,000＋住宅 20,000）

## 1回目の結果（コミット c44c4c7 の時点）

- 答え：4問とも正解（6件・IBM939・RDW／給与 350,000・手当 32,000／問題4件／新規2件を作って読み戻し OK）
- ただし **ツールが問題として示したのは仕込んだ4件のうち3件**。外字は私用領域の見えない文字に黙って変換され「0 problem(s)」。代役は、カナ「ﾐｷ」に対して漢字が3文字しか見えないことに気づき、16進を見て自力で見つけた。「報告を信じていたら見落としていた」
- コマンド 13回、つまずき 10件、誤らせそうな点 5件
- 主なつまずき
  1. コピーブックが Shift_JIS だと `utf-8 codec can't decode` で止まり、cp932 を試すヒントが無い。以後毎回 `--copybook-encoding cp932` が必要
  2. RDW 付きと気づけず、39件の問題が並んだ。RDW かどうかは16進を見て自分で計算した。`detect` は `--rdw` を受け付けない
  3. 既定の ibm930 のまま読むと、英小文字がカナに化けても警告が無い
  4. 問題の位置 `@offset` が0始まりで、layout / dump の1始まりと食い違う。OCCURS の何番目かがパスに無い
  5. SI が無い問題が、漢字が始まった項目ではなく次の項目を指していた
  6. `dump` の `--skip` / `-n` に説明が無い。`text 0E 69 41 0F`（外字）が空行・終了コード0
- 代役が挙げた直してほしいこと上位3つ：①外字を問題として報告し〓で見せる ②RDW・コピーブックの文字コード・コードページを自動で判定する ③位置を1始まりにそろえ、OCCURS の番号を付け、キー付きの問題一覧を出す

## 1回目を受けて直したこと（コミット 1d091b4）

| つまずき | 直したこと |
|---|---|
| 外字が黙って消える | kind `gaiji`（コード付き）で報告し、値は「〓」。`text` も問題として表示し終了コード1 |
| コピーブックの文字コード | 既定 auto：UTF-8 で読めなければ Shift_JIS。`note:` で知らせる |
| RDW に気づけない | ファイル全体が RDW の連なりとしてちょうど割り切れれば RDW と判定し、`note:` で知らせる。`--no-rdw` で上書き |
| コードページの既定 | 既定 auto：判定結果と理由を `note:` に出す。判定できなければ IBM930 で読み、その旨を出す。`encode` は `--codepage` 必須 |
| 位置の番号がばらばら | 問題に `pos`（1始まり）を付け、CLI の表示はすべて1始まり。数値の詳細も「byte 1 of the field」 |
| OCCURS の何番目か | パスを `ALLOWANCES(1).ALLOW-NAME` の形に |
| SI 欠落が次の項目を指す | 漢字が始まった SO の位置を指し、末尾の端数バイトと二重に数えない |
| 全件の問題一覧 | `check --key EMP-ID`：1行1問題、最後に種類ごとの件数 |
| `dump` の説明 | `--skip` / `-n` にヘルプ、見出し行、値が無いときは空欄 |

## 2回目の結果（コミット 1d091b4 の時点、同じデータ・同じ依頼・初見の代役）

| 指標 | 1回目 | 2回目 |
|---|---|---|
| 依頼4問の正解 | 4 / 4 | 4 / 4 |
| ツールが示した仕込みの問題 | 3 / 4（外字を見逃し） | **4 / 4** |
| つまずき | 10件 | **3件**（うち1件は iconv が無いだけ） |
| ebcdicjp の実行回数 | 13回（シェル全体） | 17回（help 3、実験 4 を含む） |
| 実務で使いたいか | （未質問） | 4 / 5 |

- RDW・IBM939・Shift_JIS のコピーブックは、何も指定せずに判定された。代役は `--no-rdw` と od で裏も取った
- `check --key EMP-ID` の4行だけで依頼3に答えられた
- **新しく見つかった危険**：英小文字の無い IBM939 データ（メール欄が空など）が IBM930 と判定され、カナが `iaqb jｯbn` に化けたまま「0 problem(s)」・終了コード0になる。代役が実験用のデータを作って確かめた。note の「both decode the same way」も事実と違っていた
- そのほかの指摘
  - まとめの件数（3件）と内訳（4種類）が合わない。blank を件数から外しているのに内訳には入れていた
  - `encode` のエラーが何件目のどの項目か言わない
  - `detect` の比較表示で PIC N の漢字が1バイト文字として化けて見える。判定理由がメール欄の英小文字だと分かりにくい
  - 終了コード1が「失敗」に見える（README に説明が無い）
  - `dump` で全角を含む行の列がずれる。RDW の値が見えない。「1 records」
- 代役の上位3つ：①英小文字が無いときのコードページ判定 ②件数と内訳を一致させる ③`encode` のエラーにレコード番号と項目

## 2回目を受けて直したこと

| 指摘 | 直したこと |
|---|---|
| 英小文字が無いと IBM930 と誤判定 | 「英小文字と半角カナが隣り合う」箇所を数える判定を追加（相手のコードページのカナは一部が英小文字に読める：`tﾕnﾞ`）。それでも決められず読みが違うときは「code page UNCERTAIN」を出して終了コード1。読みが同じなら「どちらでも同じ」と正しく言う |
| 件数と内訳の不一致 | 問題（件数・内訳）と blank を分けて書く：「3 problems in 3 records — bad-number 1, bad-shift 1, gaiji 1. Also 1 blank numeric field …」 |
| `encode` のエラー | 「record 1: EMP-REC.ALLOWANCES(1).ALLOW-NAME (pos 92, X(12)): … takes 14 bytes」 |
| `detect` の比較表示 | 文字項目ごとに正しく（PIC N は2バイトとして）読んだ値を並べる。理由に「IBM930 なら半角カナとして読む」と添える |
| 終了コード | README に 0 / 1 / 2 の意味を書いた |
| `dump` | 全角の幅で列をそろえる。見出しに RDW の値と長さ。単数形 |

確認：カナだけ（英小文字なし）のデータを IBM930 / IBM939 の両方で作り、どちらも正しく判定されることをテストにした。1件だけ・カナ6文字のように材料が足りないときは、黙らずに UNCERTAIN になることもテストにした。
